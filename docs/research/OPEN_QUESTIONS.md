# Open Questions and Validation Ledger

更新时间：2026-09-07

## 需补齐的产品决定（当前已有原型）

| 问题 | 为什么重要 | 如何验证 | 输出 |
|---|---|---|---|
| Android MVP 已确定；商业发行地区和渠道是什么？ | 区分私人 MVP 与商店发布承诺 | 目标用户设备分布、发行渠道与签名方案 | 发行 ADR |
| Instagram、X 等目标中，首个重点验收来源及支持边界是什么？ | 决定 payload、内容获取合法性和成功率 | 20 条真实来源 App 分享样本，不用模拟分享替代 | 内容来源 ADR |

## 必须在端到端 MVP 前回答

| 问题 | 当前判断 | 验证方式 |
|---|---|---|
| Codex 如何列出桌面项目？ | 当前代码调用 `project/list`；本轮未重跑兼容测试 | 本机 App Server schema + 开源实现 + 真实桌面对照 |
| 新会话是否正确显示在桌面项目？ | 历史审计与覆盖缺口以 验收账本（历史私人验收记录，未随公开版分发） 为准；本轮未复测 | 3 个真实项目各执行多次；新会话与独立 OS 窗口分开验收 |
| 视频必须完整下载吗？ | 完整文件最好，但某些来源可能只允许授权 API/链接处理 | 平台条款 + payload spike + 处理质量对比 |
| 只有字幕时能否继续？ | 取决于任务；UI/动效通常不能声称完整理解 | 给任务定义模态最低要求 |
| 原目录计划审批和直接执行是否满足使用预期？ | 模式已由 [ADR 0009](../decisions/0009-original-project-plan-approval.md) 确定：默认只读计划并手机批准，直接执行主动开启且只影响新提交 | 验证计划前无写入、同会话批准执行、开关不追溯放行，以及真实用户信任与完成率 |
| 审批能否在手机完成？ | MVP 有价值，但增加协议和安全设计 | App Server 审批事件 spike |

## 商业验证

| 假设 | 证据要求 |
|---|---|
| 用户比直接分享给官方 agent 更省事 | 记录完成同一任务的步骤数、补充解释次数和总时间 |
| 用户关心项目结果而非摘要 | 结果采纳/合并率显著高于只读报告使用率 |
| 使用频率适合订阅 | 第二周复用 ≥ 50%，并观察月度推算 |
| USD 12/月可接受 | 10 人中至少 3 人真实愿付费；不只问“觉得值不值” |
| 单位经济成立 | 包含内容获取、模型、存储、重试、通知、商店费和客服 |

## 外部信息核查规则

- 平台条款、API、价格、商店政策和竞品均记录来源与日期。
- 优先官方文档；推论明确标为推论。
- 实验性接口不得写入对外承诺。
- 一条成功样本不能升级为“支持该平台”。
